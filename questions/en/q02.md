# Question 2: Grain Mismatch and Duplicated Shipping Cost

**Topics:** Grain, Joins, One-to-Many, Duplicated Values

## 📝 Question

> After joining the order header table to the order line items table, why is the total shipping cost calculated redundantly (duplicated)?

## 🔢 Options

**Option 1:** Grain mismatch

**Option 2:** Low server memory

**Option 3:** Lack of an Index

**Option 4:** Using a column chart

## 💡 About this question

**Grain** means exactly what each row of a table represents.

- The **order header** table: each row = one order. "Shipping cost" is recorded at that level (for the whole order).
- The **order line items** table: each row = one item within an order.

When we join them, the order row is repeated as many times as it has items; so if an order has 3 items, its shipping cost appears 3 times in the result and the sum triples. The root cause is a **grain mismatch** (also called a fan-out).

## 🔍 Detailed review of every option

### Option 1 — ✅ Correct

> Grain mismatch

**Correct.** The "shipping cost" value lives at the order level but, after the join, it is repeated at the line-item level. This mismatch in level of detail (grain) causes the duplicated aggregation. Fixes: aggregate at the order level before joining, sum shipping only from the header table, or design the model so measures live in a fact table with the right grain.

### Option 2 — ❌ Incorrect

> Low server memory

**Incorrect.** Low server memory affects query speed or whether it completes, not the *value* of the result. With little memory a query becomes slow or fails, but it does not produce duplicated numbers.

### Option 3 — ❌ Incorrect

> Lack of an Index

**Incorrect.** An index speeds up lookups and joins and does not change the logic of the result. A missing index makes the query slower but does not duplicate rows.

### Option 4 — ❌ Incorrect

> Using a column chart

**Incorrect.** The chart type only changes how data is displayed and plays no part in computing the sum. The duplication happened earlier, at the model and join level.

## ✅ Correct answer

**Option 1**

> Grain mismatch

## 🎯 Why it is correct

A one-to-many join repeats the higher-level row (header) once for every lower-level row (item). Because shipping cost belongs to the order level, its sum gets duplicated. That is exactly a grain mismatch.

## 📌 Key takeaway

Identify each table's grain before joining or aggregating; don't sum an order-level measure over item-level data.
